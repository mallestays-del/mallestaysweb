# RCA — Malle Stays (stays-checkout-flow) "production failing" report

## Verdict
**No production failure found.** The active run `60abb00b-783b-4d8b-86f1-135791d123d9` (type: replacement) is **success**, the app is **live and serving HTTP 200**, both pods are stable with **0 restarts**, and **all required env vars are present and non-empty**. The symptom reported ("crash-loop / pods being replaced") is a misread of normal startup logs.

## Problem statement
User reports the Next.js 14 app is "failing in production" based on runtime logs showing two different pod IDs (`-6whsn`, `-m4rc8`) each printing "Ready in ~700ms", interpreted as a crash-loop. Local build passes; static scan passes.

- Pod `...-m4rc8`: phase=Running, ready=true, **restart_count=0**

The two pod IDs are the **two replicas** of this tier, not one pod restarting. `get_tier` confirms tier_0 (Starter) runs `replicas: 2, max_replicas: 2`. So exactly two pods, each booting once, each logging its own "Ready in ~700ms" — that is correct, healthy behavior. restart_count=0 on both rules out replacement/crash entirely.

### 4. MongoDB reachability

### 5. Build pipeline
Did not fail. Run `60abb00b` completed all steps and promoted; image pulled and ran. No build-log tail needed.

## Root cause
The logs shared are the **normal startup output of two healthy replicas** (tier_0 = 2 replicas). Each replica logs "Ready in ~700ms" once. There are no errors because there is no error — restart_count=0, no kill events, `/` returns 200, DB reachable, all secrets set.

## Fix
No code-side and no infra-side fix is required — the deployment is healthy. If the user is experiencing a failure in a **specific feature** (e.g., a Razorpay checkout call, a WhatsApp/Resend notification, an admin route), that is not visible at the infra layer and must be reproduced against the live URL with the exact failing request captured (path, status, response body) from browser DevTools / network tab. A present-but-wrong secret VALUE (e.g., a test Razorpay key, an expired WhatsApp token) would behave exactly this way — green infra, feature-level 4xx/5xx — and can only be confirmed from the failing request + that integration's response.

## What was verified vs inferred
- Verified: run success, 200 on `/`, both pods Running/ready/0-restarts, no kill events, all secrets present/non-empty, Mongo reachable + populated.
- Inferred (not reproduced): pod-egress-IP allowlisting (strong circumstantial evidence it's fine); correctness of secret VALUES (only presence verified).
